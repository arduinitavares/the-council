**Proposed issue 1: Begin bounded provider cleanup when a post-ready failure occurs without input**

> *This was generated by AI during triage.*

**Category/state:** `bug`, `ready-for-agent`.

**Current behavior:** `runProviderSession()` can record a provider error and request SIGTERM after readiness, yet continue waiting for input until the assignment deadline if the child stays alive. The input wait checks closure, cancellation and deadline, but not the recorded error. Forced termination becomes available only after that wait ends.

The existing queued-parser barrier prevents subsequent input delivery after a parsed error. It does not fix this cleanup delay. When no earlier error exists, absent input can instead produce an incidental filesystem error.

**Desired behavior:** A terminal pre-input failure must immediately leave the input wait and enter bounded cleanup. Missing input at the deadline must produce an explicit input-deadline outcome. Preserve the first substantive failure and existing zero-input accounting.

**Key interfaces:** `runProviderSession()`, `WrapperAssignment.deadline`, cancellation requests, process settlement receipts, `ContextWrapperTransport.cancel()` and `release()`.

**Portable offline reproduction:** Create a fresh synthetic assignment and Node fake provider with valid initialization metadata. After readiness, emit an unsupported event, ignore SIGTERM and keep the stream open. Never supply input or cancellation. Compare runs with different future assignment deadlines. Separately exercise a healthy initialized provider receiving no input, and a bound cancellation before input. Use only generated fixture data, an independent watchdog and fixture-owned process cleanup.

**Acceptance criteria:**

- A post-ready parser/stderr failure enters cleanup without waiting for input or the remaining assignment duration.
- With controlled time, the existing two-second escalation threshold is measured from cleanup entry; the cleanup budget remains at most 30 seconds, shortened by any earlier applicable cancellation deadline. These are acceptance limits, not measured runtime claims.
- Every no-input case records zero calls, no delivered input and no inference-start receipt. Late input after failure cannot change these facts.
- Missing input receives a stable, specific error; an existing provider error is retained. Pre-input cancellation cannot become an acknowledged active-turn cancellation.
- Signals affect only the owned provider group. Provider closure, group/observed-descendant settlement and timers remain independently evidenced. Unknown settlement stays unknown; exact wrapper/terminal release checks and duplicate-stop protections remain effective.

**Out of scope:** Duplicate run IDs, assignments already expired at entry, provider trust/startup admission, inference cancellation redesign, diagnostic retention and live-provider qualification.

**Proposed issue 2: Persist bounded provider diagnostics without retaining raw protocol payloads by default**

> *This was generated by AI during triage.*

**Category/state:** Recommend `enhancement`, `ready-for-agent`: this establishes an explicit privacy/provenance contract. Raw persistence is statically demonstrated; actual secret exposure or violation of an existing universal retention contract is not established.

**Current behavior:** `runProviderSession()` returns captured stdout, stderr fragments and some exception messages. `runHostWrapper()` persists that report without a diagnostic projection. Provider initialization objects can also carry unchecked extra fields into readiness/result artifacts.

`readFailure()` already retains allowlisted native-error classifications without arbitrary messages, but the provider-report path does not use that protection. Cancellation errors can propagate into journal entries and workflow outcomes.

**Desired behavior:** Persist bounded, structured provider diagnostics by default, retaining enough provenance to explain failure without storing raw protocol streams, arbitrary diagnostic messages or unchecked metadata. Keep validated Council result payloads and required private identity bindings distinct from diagnostics.

**Key interfaces:** Provider session reports, wrapper readiness/results, `readFailure()`, `PilotJournal`, cancellation results and `verifyContextResult()`.

**Portable offline reproduction:** Use a generated fake provider and the offline native-boundary harness. In separate cases, emit unique synthetic canaries in a harmless stdout event payload, stderr and an extra initialization field; inject a synthetic exception containing another canary. Inspect generated readiness, result, journal and surfaced error artifacts. Include a valid completion control. No credentials, historical captures or real provider are required.

**Acceptance criteria:**

- Synthetic diagnostic canaries are absent from persisted diagnostic fields and surfaced errors, including wrapper fallback and cancellation propagation.
- Diagnostics retain an allowlisted origin, lifecycle phase, classification/code, input-delivery state and original exit/signal values. Unknown values remain explicit.
- Arbitrary provider keys/messages are excluded. Missing metadata cannot become an asserted empty value—for example, omitted tools must not mean zero tools.
- Each diagnostic summary has a documented finite encoded-size limit, tested at and beyond its boundary; truncation/omission is explicit.
- Assignment/packet/control bindings, report hashes, native completion provenance and cleanup verification remain valid. Changing diagnostics cannot convert failure into success or weaken admission.
- Existing validated result payloads remain usable. Existing private file modes remain restrictive; sanitization neither replaces ownership checks nor launches another provider.

**Out of scope:** Historical artifact deletion/migration, unrelated packet/result/archive retention, new raw-capture modes, provider configuration/trust changes, cleanup timing and claims of an actual confidentiality incident.
