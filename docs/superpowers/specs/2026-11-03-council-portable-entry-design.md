## Intent and evidence

An explicitly invoked Council skill should be understandable and usable from a complete clean installation in an unrelated requesting project. Package instructions must locate their own resources without the maintainer's home directory. Required execution-host policy and operational guidance must remain external, authoritative prerequisites. Portable entry does not mean an uncredentialed installation can perform inference or that the current live route is qualified.

## Approaches

1. **Correct the three entry documents and verify the installed artifact.** Keep package-relative resource links, identify external prerequisites on the execution host, and give native and retained entry separate preparation instructions. This is the recommended approach: the observed launcher behavior already provides the needed package/requesting-project separation.
2. **Bundle host policy and host skills into the package.** This would make links self-contained, but would replace canonical execution-host authority with a package snapshot and could supply mismatched Orca guidance. It conflicts with the required policy boundary and is rejected.
3. **Add a resolver, installer or common request wrapper.** This would introduce product behavior and risk merging two incompatible request contracts without evidence of a launcher defect. It is outside this documentation correction and is rejected.

The recommendation is the author's design choice, not a recorded user approval. No new package layout, command, flag, schema, dependency or automatic host setup is proposed.

The coordinator must obtain explicit user approval of this revised design before the next implementation-planning step, and preserve the applicable independent plan/change review and acceptance gates. Accepted review findings and completion of this revision do not approve the design or implementation.

## Resource ownership and resolution

Resolve the installed skill's canonical location before following its package references, including when the skill or launcher is reached through a personal symlink. The requesting project's cwd is not the package root. This proposal requires the complete current package tree and prepared runtime dependencies; copying only `SKILL.md` or only the skill directory is insufficient. Extracted-package readiness remains unproven until the checks below pass.

| Resource | Resolution and authority |
| --- | --- |
| Communication, native first-use instructions and native roster | Keep `references/communication.md`, `references/first-use.md` and `references/first-use-roster.yaml` relative to the canonical installed skill. |
| Runbook and launcher | Keep `../../docs/runbook.md` and `scripts/run-council.mjs` relative to that same skill. Preserve the launcher and built CLI positions in the package. |
| Retained default configuration and built runtime assets | Remain package-owned at their current locations, including `council.yaml`, both built CLI entries and `dist/store/schema.sql`. No lookup through the requesting project or maintainer checkout. |
| Execution-host model policy | The canonical host file is `~/.agents/policies/model-policy.md`. `~` means the execution host's home, not the package author's home or a literal CLI expansion. The caller supplies its resolved absolute path; discovery requires realpath equality with that host's canonical file and reads its exact bytes. No bundled copy or arbitrary substitute is accepted. |
| Orca CLI and orchestration skills and guides | Resolve the installed `orca-cli` and `orchestration` skills from the execution host's skill catalog/instruction setup. Read their actual `SKILL.md` files and required version-matched references for the selected Orca installation. Do not guess a plugin cache version, reuse the maintainer's installation path or turn a historical Orca version into a supported-version floor. |
| Retained handoff skill | Resolve the required installed `handoff` skill on the execution host for the retained structured-handoff procedure. Keep its temporary-location and sensitive-exclusion requirements. It is not a package-relative asset. |
| Language guidance | Resolve the required installed `simplified-technical-english` skill on the execution host for packets and reports. Preserve exact identifiers, paths, commands, quotations and uncertainty; do not claim dictionary or full ASD-STE100 conformance from this correction. |

These are resolution instructions, not a new runtime discovery feature. If an applicable external prerequisite cannot be resolved or read, the caller reports the missing resource and expected host location or catalog entry, stops the affected launch and leaves unrelated authorized work available. Missing or ambiguous version-matched guidance is not permission to use an arbitrary copy. This result is a caller prerequisite report, not an invented CLI status or qualification receipt. Configuration-only inspection remains possible without those live prerequisites.

Caller-side reading of policy and guidance before launch is a procedural requirement. It is distinct from executable ordering: `src/pilot/cli.ts:132` resolves the supplied policy path and can reject a nonexistent path before cache/client creation. Inside `NativeHostInspector`, `src/pilot/discovery.ts:40` resolves the canonical host path and compares realpaths before the first injected status command at line 44. Policy bytes are read at line 92, after status, registry and workspace checks. Do not claim that policy-content readability or nonempty content is checked before those operations, or that the CLI implements host skill/guide discovery.

Do not download host guidance, install skills, create policy files, change permissions, start the Orca desktop or register a workspace automatically. Reuse existing applicable authorization while satisfying actual host controls; the documentation must not introduce a new routine consent interview or bypass an actual refusal.

## Keep the two entry procedures distinct

The skill first requires explicit invocation and identifies which existing entry the caller intends. Native preparation must appear before the retained-only handoff procedure so a reader does not construct a retained request for `native`.

| Concern | Native supplied-text entry | Retained controller entry |
| --- | --- | --- |
| Selection | Explicit `native` following the packaged launcher. | Existing `start`, `inspect`, `respond`, `resume`, `cancel` and qualification commands. |
| Request | The existing native JSON fields: `runId`, `candidate`, `suppliedText`, `maxProbeCalls`, `maxTopicCalls`, `deadline`, `workerTimeoutMs` and optional `proofTtlMs`. Scope supplied text and exclude secrets and unrelated conversation. | The existing `topic`, structured `handoff`, `scope` and optional run controls. Keep `runInputSchema` and `handoffInputSchema` authoritative; preserve the runbook's field guidance, explicit empty arrays where allowed, worker access and authorized sources/commands/effects. `suggestedSkills` still requires at least one entry. |
| Handoff preparation | Do not require the controller's `handoff` object or transform native supplied text into that format. Native input remains its own contract. | Require the host handoff skill and preserve the controller-created mode-0600 OS-temporary handoff and `needs_context` behavior. |
| Path rules | Explicit requesting `--workspace`; relative input/config/policy paths resolve there. Omitted configuration uses the packaged native roster. `--orca`, when supplied, must identify the intended absolute executable. | Retain the package default configuration, invocation-cwd resolution for an explicit `start --config`, frozen saved configuration and rejection of `--config` on other retained commands. |
| Operational state | Preserve native bounds, proof cache, journal, no automatic relaunch/resume and exact owned-resource settlement requirements. | Preserve saved state, queued-versus-applied controls, caller-authored candidates, common question batches, bound ballots, temporary context, resume counters and recovery fences. |

Use quoted generic absolute installed paths in runnable examples, with a distinct absolute requesting-project path. The runbook's retained examples are already labeled `From this checkout`; preserve that distinction. Explain that shell expansion, not Node's argument parser, expands a home shorthand. POSIX live-entry examples must name the canonical policy with `--policy "$HOME/.agents/policies/model-policy.md"`, or a fully specified absolute canonical path. Quoting a literal tilde, as in `"~/.agents/policies/model-policy.md"`, prevents that shell expansion and is unsuitable.

For example, the documented native invocation can have this shape after all host and operational gates pass and the generic installation/requesting-project paths are replaced:

```sh
node "/absolute/installed/the-council/skills/the-council/scripts/run-council.mjs" native \
  --workspace "/absolute/requesting/project" --input "request.json" \
  --policy "$HOME/.agents/policies/model-policy.md" --json
```

No example may imply that a copied policy file, an expired example deadline, an explicit roster or a valid configuration authorizes inference. Keep the existing source-audit procedure and its bound snapshot/Run/Task/Dispatch provenance. If editing its command examples, replace raw angle-bracket shell arguments with safely quoted task-specific variables populated from actual reviewed records, such as `--hash "$council_snapshot_sha256" --run "$council_native_run" --task "$council_native_task"`. Unset variables, example values or invented native IDs are not valid substitutions. The separate Task spec literal `Council control audit sha256=<snapshot-hash>` describes an existing binding contract, not a shell command to execute.

Source schema paths may remain clearly labeled contributor references. Installed users must have sufficient preparation guidance in the shipped documents and the unchanged CLI validation; do not make an unshipped source checkout a new entry prerequisite.
